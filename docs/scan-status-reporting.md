# 扫描状态增量上报与停止收尾

攻击模式审计和迭代攻击模式审计在运行时持续登记任务及状态。停止复用这些记录，不重新生成并上传全部待执行任务的取消快照。扫描结果、任务身份、成功产物复用和续扫选择规则保持原有语义。

## 运行与停止

1. Agent 与后端协商 `server_owned_pattern_task_settlement` 能力，且取得有效执行轮次后，`pending/queued/running` 与任务终态均进入已有的 SQLite 可靠上报队列。相同业务内容不重复入队；同一任务尚未确认的快照可以被更新快照替换。排队成功后即由队列负责重试，不增加开始模型任务前的服务端确认屏障。
2. 继续使用单任务 `POST /api/agent/scan/{scan_id}/threat-pattern-audit-task`，附带 `execution_revision`、`report_agent_session_id`、`report_sequence`。报告会话独立于产物 `output_source`，复用结果时保留原产物来源。
3. 用户停止、扫描结束或当前执行的引擎结束时，后端在终态事务中用集合 SQL 将已有 `pending/queued/running` 改为 `cancelled`。仅取受影响的引擎 ID，不读取或重新解析每个任务、线索和漏洞正文；已完成、失败、超时及已替代任务不被覆盖。事务成功后，受影响的集合发出一条 `change: task_status` 失效通知。
4. Agent 取消逻辑仍结束本地任务，但仅为本轮实际执行过的未完成任务补报新增终态信息，例如最终 Session 来源。纯待执行任务不产生停止上报。已有运行时待发送报告继续可靠重试；它们是未确认的增量，并非停止时重新汇总的快照。

不支持该能力的旧后端/Agent 保留原有上报方式。完整消除停止逐任务取消请求，需要同时更新后端和 Agent。旧版报告不能覆盖已接收新协议报告的同一任务。

## 续扫、竞态与恢复

- 任务报告与终态更新使用相同的扫描行事务边界。旧轮或旧会话的报告返回 `409 stale scan execution`，可靠队列按已有规则丢弃失效执行报告。
- 相同会话、轮次下的重复/乱序报告不再发布业务变更通知；内容未变但序号更新时只前移标记，不重写业务时间或汇总计数。
- 停止后迟到的非终态报告仍落为取消，不能恢复运行；同一执行在停止竞态中实际完成的结果可以补入。随后迟到的取消不能覆盖已完成结果。
- 手动或自动续扫取得新执行轮次后，未完成任务可以重新登记为待执行。成功任务、结果索引、原 Session 来源与迭代线索保留；Agent 重连接管同一轮次只更换报告会话，不能重新打开终态任务。
- 未访问到的历史迭代后续任务也由后端关闭，不要求 Agent 在停止时重新读取并逐项上传。启动/恢复派发失败同样关闭已有未完成任务。用户停止仍暂停自动续扫。
- 引擎终态与扫描结束报告的本地去重键也包含执行会话和轮次。旧轮未确认时，新轮结束报告不会占用旧队列位置而越过本轮任务结果；重连仍能识别各轮待确认的结束报告。

## 数据库存储开销

SQLite 与 PostgreSQL 启动时自动为原任务表增加三个内部字段，历史行默认 `0 / 空字符串 / 0`；不新增任务历史快照表，不批量改写历史状态。集合更新利用已有扫描 ID 前缀索引，保留状态统计触发器；未变化的序号标记不会触发状态计数改写。

Agent 序号与报告入队在同一事务提交，避免额外一次同步落盘。同一服务端、Agent 会话共用递增序号，单任务序号允许有间隙；序号表不随任务数或续扫轮次增长。确认后的待发报告按原规则删除。运行时可靠性会增加中间状态的本地持久化成本，但相同内容不重复写、未确认快照合并，并消除停止时的待执行任务写入。

集合 SQL 的语句数与提交次数是固定的，数据库仍需更新实际受影响的行及其计数，耗时不是常数。Agent 仍遍历已有内存任务结束本地状态，不重新收集任务正文或请求服务端列表。

## 页面刷新

审计集合第一批变更等待 150 ms 合并，后续刷新每秒至多一轮；读取期间发生的新变更保留一次后续刷新。概览状态、终态核对和 ETA 独立推进。未显示的审计页保留缓存失效标记，进入对应页面再刷新已加载的分页跨度。迭代页只读取自己的引擎分页，不同时重复读取通用任务列表。

状态或取消 Session 元数据变化不会重新读取关联结果；新增结果索引、漏洞内容及显式结果失效仍触发读取。任务历史由完成计数、实际历史变化、执行轮次和显式失效驱动，不再依赖模型池心跳时间。停止按钮仅刷新必要状态，去误报确实被停止时才同步复核状态。断线、事件丢失和新轮次仍有相应缓存失效；旧轮通知不会污染续扫的新状态。

## 验证与基准

本地 SQLite 存储基准使用 `c7540c9` 的原始逐任务写入方法作为基线，同一 schema、1000 个未完成任务及一个已完成任务，五轮中值：

| 指标 | 原逐任务取消 | 当前集合收尾 |
| --- | ---: | ---: |
| 存储耗时 | 1506.896 ms | 21.336 ms |
| 应用 SQL 次数 | 3003 | 5 |
| 其中任务表 SQL | 2000 | 2 |
| 提交次数 | 1001 | 1 |

执行 `PYTHONPATH=. python3 scripts/benchmark_pattern_task_settlement.py` 可复现。初始数据准备、结果校验、HTTP/SSE 和 Agent 开销均不在计时内，SQL 次数不展开触发器；每轮断言已完成任务的来源、结果索引和线索未变。`--trace-memory` 可单独测 Python 分配，但会影响计时。以上不是生产端到端耗时承诺。

前端固定场景（150 条已加载任务、六条间隔约 200 ms 的取消通知）分页 GET 从 18 次降为 6 次，概览读取从 6 次降为 2 次，没有结果正文重读。1000 条集中通知合并成一轮，迭代页不额外发出通用任务列表 GET。这些是本地受控测试，并非生产访问日志统计。

已验证的重点包括：

- SQLite 与真实 PostgreSQL 的跨连接停止竞态、迟到报告、会话接管、执行轮次隔离、成功结果保留、汇总计数、启动失败和旧 SQLite 表迁移。
- 1000 个纯待执行任务停止不产生新队列写入；重复运行快照不增加写入；序号与报告共用一次提交；旧确认不会删除新快照；队列重新打开后序号继续递增。
- 手动续扫、自动续扫、Agent 重连、候选恢复、威胁覆盖恢复、可靠队列与 SSE 回归；前端状态/结果区分、跨页缓存、续扫、历史分页、分享请求和构建。

跨层恢复回归 204 项通过，未提供 DSN 的这一轮有 18 项跳过；随后使用临时真实 PostgreSQL 的服务与续扫回归 83 项通过。存储回归 68 项通过，追加边界的最新 SQLite/PostgreSQL 专项 27 项通过（这些运行有重叠，不累加为独立测试数）。前端先前全量 497 项通过，最终修订分别通过相关页 103 项、最新刷新/结果 28 项与续扫进度 40 项检查，构建成功。

最后修正跨轮结束报告队列位置后，Agent 增量上报、两类攻击模式引擎、Reporter 和可靠队列共 168 项通过，包括旧轮积压、新轮结果先于新轮结束上报的用例。

扩展引擎/静态状态回归有 60 项及 21 个子测试通过，另一个已有失败是 `MiningEnginePersistenceTests.test_migration_normalizes_builtin_engine_labels_by_id`：旧引擎名称没有按该测试预期回写。在隔离的未修改 `c7540c9` 上复现相同失败，未扩大本次变更修改历史迁移。沙箱内挂起的异步测试已中断并在沙箱外完成，不计作通过。

本次仅完成本地实现与验证。部署时需更新后端和前端、更新并重启 Agent；生产环境可按方法与路径统计停止窗口的请求量，区分实际运行任务的收尾与已有可靠队列重试。
