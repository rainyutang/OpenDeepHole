# 扫描整体进度与预计剩余时间

扫描详情首页和共享扫描首页在“当前扫描”下显示整体进度条及预计剩余时间。此处的估算独立于静态候选审计的 `progress`；任务数量、预计完成时刻和任务生成说明不在新卡片中展示。

## 计算口径

- 覆盖当前扫描已经创建的任务，包括独立去误报和漏洞验证。后续新任务进入队列时重新计算，百分比可以下降。
- 当前模型池的计划、排队和运行任务与完整终态历史合并，按逻辑任务 ID、计划任务 ID 和最新 revision 去重；不会使用分页任务列表或任务总数历史峰值代替完整数据。
- 复用业务分类：威胁分析、候选点审计、威胁审计、威胁模式审计、去误报、漏洞验证等。威胁分析内部各阶段共用该类别的平均值。
- 每类只采纳成功、有限且大于零的执行耗时。当前扫描达到 3 个样本时使用全部当前样本均值；不足时按完成时间从新到旧补充同一用户、同一 Agent 近 30 天已收到的成功任务，补至 3 个。已有不足 3 个样本时也可估算。
- 独立任务回执的 Agent 稳定身份优先于扫描当前归属，防止换 Agent 续扫后混入其他机器的耗时。无回执的旧记录仅按保存的稳定 Agent key 回退，缺少 key 时不参考历史扫描。
- `logical_duration_seconds` 记录同一逻辑任务各次模型 lease 的累计执行时间，包括自动重试、格式修复和原 Session 纠错，排除排队等待。旧任务使用原 `duration_seconds`；模型单次 lease 的耗时统计保持原义。

每个任务以所属类型平均耗时作为权重。已结束任务（含失败、取消）计满权重；运行任务使用此前尝试耗时加当前执行耗时，最多计入该权重的 90%；待执行任务不计完成权重。整体进度为完成权重除以全部权重。任一类别缺少样本时回退到已结束任务数比例，暂不显示剩余分钟数。

剩余时间取以下估计的最大值：剩余权重总量除以有效并发、最长单任务残余、高能力任务的容量瓶颈及中高能力任务的共同容量瓶颈。有效并发优先采用本扫描实际运行数，尚未运行时采用当前启用且可用的模型容量。这是近似估算，不预判未来任务、模型开放时段或其他扫描未来的资源竞争。

业务层已创建但尚未进入模型队列的候选审计、威胁审计和验证任务也计入进度；其调度信息齐备前，剩余时间显示“估算中”。

## 状态与刷新

- 主扫描和已创建的后续任务全部结束才显示 `100%` 和 `0 分钟`；执行期间最高显示 `99%`。
- 启动准备、缺少样本或任务正在转交调度时，剩余时间显示“估算中”。离线、阻塞、异常、取消时显示“暂无法估算”。
- 独立验证通过自身 execution owner、revision 和 Agent session 上报模型池，主扫描结束不会清除仍有效的验证任务。
- 复用首页每 10 秒刷新，覆盖主扫描结束后继续运行的复核、验证；相关 SSE 事件触发刷新。前端按执行版本和计算时间选择较新摘要，旧响应不能回滚估算。

## API 与兼容性

`GET /api/scan/{scan_id}` 和 `GET /api/v2/scans/{scan_id}/overview` 增加可选的 `progress_estimate`：

```json
{
  "progress": 0.68,
  "remaining_seconds": 2100,
  "state": "ready",
  "calculated_at": "2026-11-09T12:00:00+00:00",
  "execution_revision": 2,
  "active": true
}
```

`state` 为 `ready`、`estimating`、`unavailable` 或 `complete`；不能估算时 `remaining_seconds` 为 `null`。`active` 指示是否仍存在正在执行的扫描或后续工作。共享接口复用同一计算，历史样本只影响聚合值，不返回其他扫描的任务内容。

存储查询只读取历史元数据。SQLite 和 PostgreSQL 启动时自动创建 Agent＋上报时间索引，无需改写历史任务。上线需要同步更新后端、前端和 Agent；旧 Agent 数据仍可估算，但旧重试耗时与独立验证队列的完整性取决于原上报数据。
