# 误报模式与 13 项反方挑战

对每个漏洞逐项回答：

1. 危险值是否实际上来自可信常量或仅由特权组件写入？
2. 上游调用者是否施加了报告遗漏的长度、类型、范围或状态约束？
3. 框架或 API 是否自动完成参数化、转义、边界检查或权限检查？
4. 数据是否在到达汇点前被规范化、截断、编码、复制或验证？
5. 声称的路径是否为死代码、仅测试代码、不可构建代码或实际配置未启用代码？
6. 错误分支是否在危险操作前已经返回、抛出异常或终止事务？
7. 语言类型系统或内存安全运行时是否完全阻止该漏洞类别？
8. 并发模型是否真的允许两个参与方同时访问该状态，且攻击者能影响时序？
9. 数学约束是否使溢出、越界、负值或截断条件不可能出现？
10. 攻击者触发前是否已经需要相同或更高权限，使声称的权限提升无意义？
11. 结果是否只有日志噪声、无价值数据、瞬时错误或可忽略的资源消耗，而没有安全边界影响？
12. PoC 是否依赖禁用校验、修改生产逻辑、不真实 mock、未部署配置或无法满足的前置条件？
13. 是否把纵深防御缺失误认为主要控制失效，或反过来把纵深防御存在误认为漏洞不存在？

## 红旗

- 只引用危险函数，没有入口和调用者。
- 只说“用户可控”，没有证明谁写入该数据。
- 只给理论复杂度，没有构造最坏输入和资源比例。
- 只展示崩溃栈，没有证明远程/低权限攻击者可达。
- 只引用某个库的一般行为，没有核对版本和配置。
- PoC 使用占位符、预期输出或人为绕过。
- 结论使用“看起来”“大概率”“通常”而缺少代码证据。
