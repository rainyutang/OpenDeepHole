# 深度验证

复杂漏洞按依赖波次执行。若从标准路径升级，复用已经完成的证据，只补剩余阶段。

## 阶段 1：数据流分析

### 1.1 信任边界与完整路径

列出源、汇、每个中间转换和校验，至少向上追踪两层调用者，并引用具体 `file:line`。

### 1.2 API 合约与安全保证

核对实际版本和配置，判断框架、库或语言是否提供边界检查、参数化、自动转义、类型安全等保证。

### 1.3 环境保护

识别编译器、运行时、操作系统、容器和框架保护，并分类为“完全阻止”或“仅提高利用门槛”。

### 1.4 交叉验证

搜索相似实现、测试、安全评审记录、TODO/FIXME 和相关 Git 历史。

## 阶段 2：可利用性验证

阶段 2 只能在阶段 1 完成后开始。

### 2.1 攻击者控制

证明真实输入向量、控制程度（完全、部分、无）及中间限制。

### 2.2 数学边界

列出类型、位宽、符号性、全部约束、转换和逐步推导。给出可触发具体值，或证明条件不可能。

### 2.3 竞态可行性

核对并发模型、同步原语、窗口大小、攻击者能否扩大窗口。非并发问题明确写不适用。

### 2.4 对抗综合

综合控制、边界和竞态证据，写出最现实攻击路径、所需能力和可行性。

## 阶段 3：影响评估

阶段 3 依赖阶段 2。

- 分别评估机密性、完整性、可用性、认证和授权边界。
- 证明影响是安全影响还是纯运维健壮性问题。
- 对 DoS 量化输入与资源消耗比例、可回收性、重启行为和持续时间。
- 区分主要控制与纵深防御；后者通常不能否定漏洞。

## 阶段 4：PoC

阶段 4 依赖阶段 3。

1. 4.1：始终提供带数据流图的具体伪代码 PoC。
2. 4.2：可行时创建并运行可执行 PoC；不可行必须给出具体原因。
3. 4.3：可行时创建并运行单元测试 PoC；不可行必须给出具体原因。
4. 4.4：创建正常输入的负向 PoC，展示漏洞前置条件。
5. 4.5：验证所有 PoC 没有人工绕过，并确实证明声称的影响。

## 阶段 5：反方审查

阶段 5 依赖阶段 4。逐项回答 `false-positive-patterns.md` 的 13 个问题，主动寻找否定当前结论的证据。

## 六道门

最后按 `gate-reviews.md` 评估六道门。所有门都必须有证据；任何失败都产生 FALSE POSITIVE。技术失败、缺阶段或证据不完整保持未完成。

## 执行约束

- 不得越过依赖门提前执行后续阶段。
- 同一阶段内独立子项可以并行，但必须全部收集后才能进入下一阶段。
- 每个事实引用具体代码位置；无法确认时明确记录未知，不得使用“可能”“大概”代替证据。
