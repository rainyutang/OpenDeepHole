# 标准验证

标准路径适用于主张清晰、单组件、无并发且数据流直接的问题。按顺序完成，不能只凭危险模式下结论。

## 1. 主张一致性

- 用一句话写清攻击者输入、代码缺陷、触发条件和安全影响。
- 核对报告中的文件、行号、函数、漏洞类别是否与真实代码一致。
- 如果主张含糊、位置错误或无法形成可验证因果链，记录证据并进入六道门，不要自行改写成另一个漏洞。

## 2. 源到汇数据流

- 找到真正的外部输入源和最终危险操作。
- 至少向上检查两层调用者。
- 记录每个校验、转换、截断、编码、权限检查和错误处理。
- 标明每个值的信任级别及攻击者控制程度。

### 升级检查点一

出现跨三个以上模块、复杂别名、异步回调、竞态、难以确定的 API 合约或无法完整追踪的数据流时，停止标准路径，保留当前证据并升级到深度路径。

## 3. 可达性与可利用性

- 证明攻击者能到达该调用路径，而不只是函数理论上可调用。
- 证明攻击者控制的具体值能够穿过全部校验。
- 对边界问题写出变量类型、约束和逐步不等式。
- 对非边界问题明确写“数学边界不适用”及原因。
- 对非并发问题明确写“竞态不适用”及原因。

## 4. 真实影响

分别检查：

- 机密性：是否泄露有价值的数据。
- 完整性：是否能修改数据、状态或执行流。
- 可用性：是否造成可靠崩溃、死锁、资源耗尽或有意义的放大。
- 认证边界：是否绕过身份确认。
- 授权边界：是否越权访问或操作资源。

DoS、崩溃和资源耗尽属于真实安全影响候选，不能只因不是代码执行就丢弃。区分主要安全控制和纵深防御；纵深防御存在通常只提高利用门槛。

### 升级检查点二

影响依赖部署环境、组合条件、跨组件状态、复杂攻击前置条件，或无法通过直接实验/代码证据确认时，升级到深度路径。

## 5. 最小 PoC 与反例

- 给出具体输入和从入口到危险操作的伪代码 PoC。
- 可行时运行最小可执行 PoC 或单元测试并记录真实输出。
- 给出正常输入的反例，并写清触发漏洞必须满足的差异条件。
- 不得通过禁用校验、修改生产逻辑或不真实的 mock 制造成功。

## 6. 13 项反方挑战

逐项应用 `false-positive-patterns.md`，不能以“均不适用”整体跳过。

## 7. 六道门

按 `gate-reviews.md` 分别评估流程、可达性、真实影响、PoC、数学边界和环境门。

- 全部通过才是 TRUE POSITIVE。
- 任一失败即是 FALSE POSITIVE。
- 输出或证据不完整时是未完成，不能生成二元结论。
