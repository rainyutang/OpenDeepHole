# 按漏洞类别补充验证

以下要求叠加在通用阶段之上。

## 内存破坏

先检查语言安全边界。安全 Rust、未使用 `unsafe.Pointer`/cgo 的 Go、未调用原生代码的 Java/C#/Python 通常会阻止传统内存破坏。若存在不安全边界，证明具体被破坏的对象、大小、偏移、攻击者控制程度、分配器和加固，以及它是否形成有用原语而非只崩溃。

UAF 需追踪释放、复用和替代对象；类型混淆需证明真实类型不匹配和可利用的解释差异。

## 逻辑漏洞

对照规范、RFC 或设计文档，绘制全部状态迁移和隐含假设。认证/授权问题必须检查所有备用路径和二次检查，不能因边界检查正常就否定逻辑漏洞。

## 竞态与 TOCTOU

证明参与线程/进程、同步原语、实际窗口及攻击者扩大窗口的方法。文件系统 TOCTOU 还要证明攻击者能在检查与使用之间控制路径。

## 整数问题

记录每个变量的位宽和符号性，追踪转换、提升、截断与符号扩展。区分 C/C++ 有符号溢出的未定义行为和无符号回绕。证明异常值最终进入分配、索引或循环等危险用途。

## 密码学

对照当前标准和实际参数，验证随机源、播种、nonce 是否真实复用、时序测量是否有足够信噪比，并尽量使用规范测试向量或参考实现。

## 注入

追踪真实外部输入到 SQL、命令、模板、HTML 或路径汇点，核对上下文相关转义、参数化、规范化和编码转换是否启用且可绕过。

## 信息泄露

指出泄露的具体数据及攻击价值。证明内存在读取点确实未初始化；时序侧信道需证明可收集足量精确测量；错误信息需证明会返回攻击者而非仅写服务端日志。

## 拒绝服务

量化攻击输入与 CPU、内存、句柄、线程、磁盘或重启成本的比例。证明最坏输入、资源是否回收、触发可靠性、自动重启行为和服务中断持续时间。DoS 是可用性安全影响，不能自动判为误报。

## 反序列化

证明攻击者控制的数据到达真实反序列化调用，核对库和版本、类型限制/白名单/过滤器，并证明运行时依赖中存在可用 gadget 链。没有 gadget 链时应区分设计风险和可利用漏洞。
